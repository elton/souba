# Cloudflare Worker 出口对行情源的可达性验证（阶段 0）

**日期：** 2026-08-26 · **执行者：** 实测，非推演 · **对应：** 实施计划 Task 1

---

## 结论先行

**腾讯和新浪的四个接口，从 Cloudflare Worker 全部打得通，没有任何封禁迹象。**
这意味着「每日增量追加历史数据」这条路可以留在 Worker 上跑，不必退回到「TUI 推送」的备选方案。

之前的担忧是有依据的 —— Yahoo 对数据中心 IP 第一个请求就 429，而 Worker 正是从共享数据中心 IP
出站。但腾讯和新浪并不这么做：**连打 6 次（含两次仅隔 7 秒的密集请求）全部 200，且第 6 次比第 1 次更快。**

三点次要但影响实现的发现：

1. **`TextDecoder('gbk')` 在 workerd 里可用**，中文完全不乱码。Worker 侧解析行情没有障碍。
2. **CPU 消耗只有 2–3 ms**（免费版上限 10 ms），即使解码一个 647 KB 的响应体也是如此。
   余量比预想宽裕，但这只覆盖 fetch + 解码，**不含 `JSON.parse` 与 D1 写入** —— 见下文的边界说明。
3. **新浪那个「必须强制 HTTP/1.1 否则挂住」的坑，在 Worker 上不存在。** Worker 的
   `fetch` 走 Cloudflare 自己的出站栈，直接返回 200。这个约束只适用于本机 curl / reqwest。

### GBK 解码验证

`TextDecoder('gbk')` 在 workerd 里工作正常，未乱码：

```
v_sh600519="1~贵州茅台~600519~1303.38~1304.00~1300.00~14512~...~20260826120552~-0.62~-0.05~1314.45~1295.00~..."
```

**不需要手写 GBK 码表，也不需要换 UTF-8 源。**

| `tencent-kline-day` | 200 · 723 ms | 200 · 1631 ms | 200 · **358 ms** | 无 |

**没有出现劣化。** 第 2 次整体偏慢、第 3 次又回到最快，这是网络抖动的形状，不是限流的形状 ——

30 秒间隔可能太温和，所以又追加了三次，其中第 5、6 次**仅隔约 7 秒**：

## CPU 预算实测

用 `wrangler tail --format json` 抓到三个真实调用样本：

| 样本 | outcome | cpuTime | wallTime |
|---|---|---|---|
| 1 | ok | **2 ms** | 2411 ms |
| 2 | ok | **2 ms** | 2797 ms |
| 3 | ok | **3 ms** | 2885 ms |

免费版上限是 **10 ms CPU / 次调用**，wall-clock 不限。本次用掉 20–30%。

值得注意：这 2–3 ms 里已经包含了对 `sina-kline-full` 那 **647 KB** 响应体的完整 GBK 解码
（`TextDecoder.decode(buf)` 解的是整个 buffer，`.slice()` 是解码之后才发生的）。
**原生 `TextDecoder` 解 647 KB 几乎不花 CPU。**

### 这个数字的边界 —— 不要过度外推

本次测的是 **fetch + 解码 + 截取**。**没有测**：

- `JSON.parse` 一个大 payload（`../CLAUDE.md` 记录典型成本 10–20 ms，会直接顶穿上限）
- D1 写入
- 多 symbol 循环

所以「2 ms」不能读成「Worker 的 CPU 很宽裕，什么都能干」。它只说明**网络 I/O 与解码本身不是瓶颈**，
瓶颈仍然在解析与写库 —— 这与设计文档的原判断一致，没有推翻它。

## 结论：Worker 能否承担每日增量追加？

### 能，但要按「小 payload」来设计

**网络可达性这一关过了** —— 这是本次要回答的问题，答案是肯定的。腾讯和新浪都不对
Cloudflare 数据中心 IP 做区别对待，港股实时也没有被降级。

CPU 这一关**取决于怎么写**，而不是取决于出口：

- ✅ **可行**：Cron 每日拉取「最后 1–2 根 bar」的小请求，`JSON.parse` 几 KB，写入 D1。
  新浪 kline 支持 `datalen` 参数，把它压到 5 而不是 6000，payload 就从 647 KB 降到 ~500 B。
- ❌ **不可行**：在 Worker 上 `JSON.parse` 647 KB 的全量历史。这必然超 10 ms。
  **冷启动全量回填仍然必须留在 Rust TUI 里**，由 TUI 分批 POST 给 Worker 落库 —— 这一点没有变化。

### 替代方案（本次未被触发，留档备查）

如果将来腾讯/新浪开始对 Worker 出口 IP 封禁（IP 信誉是会变的，本次结论有时效性），
退路是：**由 TUI 拉取数据后 POST 给 Worker 落库**，Worker 退化成纯存储端点，不再自己出站抓数据。

这条退路的代价可以接受，因为架构本来就把实时行情放在 TUI 直连：Worker 出口若失效，
只影响「无人值守的每日追加」，不影响看行情。**代价是必须每天至少开一次 TUI，
否则历史数据会出现空洞。**

### 对阶段 1 架构的影响

**无。** 实时行情本来就走 TUI 直连（那是 10 ms CPU 上限逆推出的结论，与本次验证无关），
本次结果只是把「每日增量追加」这条路从「存疑」变成「可用」。阶段 1 可以照原计划推进。

## 对实施计划的两处偏离（均已实际执行）

1. **依赖版本。** 计划写的 `@cloudflare/workers-types@^4.20260801.0` 在 npm 上不存在 ——
   该包已经进到 5.x（最新 `5.20260826.1`）。按最新稳定版落地：
   `wrangler@^4.126.0` · `@cloudflare/workers-types@^5.20260826.1` · `typescript@^7.0.2`。
   pnpm 要求显式批准 `esbuild` / `workerd` 的构建脚本，故新增了 `worker/pnpm-workspace.yaml`。

2. **`sample` 截取长度 120 → 1200。** 120 字符只够看到第一只标的的前几个字段，
   看不到 `r_hk00700` / `usAAPL` 有没有数据 —— 而「四市场一个接口全覆盖」正是腾讯接口的核心价值，
   值得一并确认。上文的「四市场覆盖确认」一节就是这个改动换来的。
   代码保持在 1200，与实际部署的版本一致。
