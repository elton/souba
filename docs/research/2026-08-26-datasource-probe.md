# 免费行情数据源实测报告

**日期：** 2026-08-26
**方法：** 从**中国大陆以外**的 IP（日本，JST）用 `curl` 直接调用各接口。
所有结论来自实际响应，不是文档或记忆。复现脚本：[`scripts/probe-datasources.sh`](../../scripts/probe-datasources.sh)。

> 为什么要从海外 IP 测：后端计划跑在 Cloudflare Workers 上，出口是全球数据中心 IP。
> 一个「在国内能用」的接口对本项目毫无意义。

## 1. 腾讯 `qt.gtimg.cn` —— 一个源覆盖四市场

最重要的发现。同一个接口用不同代码前缀覆盖全部四个市场，免费、无需注册、无 API key。

```
https://qt.gtimg.cn/q=sh600519    # A股 上交所
https://qt.gtimg.cn/q=sz000001    # A股 深交所
https://qt.gtimg.cn/q=hk00700     # 港股
https://qt.gtimg.cn/q=usAAPL      # 美股
https://qt.gtimg.cn/q=jp7203      # 日股
```

**返回是 GBK 编码，不是 UTF-8。** 不解码会得到乱码股票名。这是接入时最容易踩的第一个坑。

响应是 `~` 分隔的字符串，形如：

```
v_sh600519="1~贵州茅台~600519~1308.65~1304.00~1300.00~10507~...~20260826103558~4.65~0.36~..."
```

### 各市场实测延迟

测试时刻：北京时间 `10:37:16`（A股与港股盘中）。

| 市场 | 返回时间戳 | 相对当时 | 判定 |
|---|---|---|---|
| A股 `sh600519` | `20260826103558` | 同秒 | **真实时** |
| 港股 `hk00700` | `2026/08/26 10:20:55` | 慢 ~15 分钟 | **延迟** |
| 日股 `jp7203` | `2026-08-26 10:17:56` | 慢 ~19 分钟 | **延迟** |
| 美股 `usAAPL` | `2026-08-25 16:00:01` | 美东收盘时刻 | 收盘价，正确 |

两次独立测量：港股慢 15.0 / 16.3 分钟，日股慢 19.3 / 16.3 分钟 —— 都在 **15–20 分钟**区间浮动，不是一个固定值。

港股与日股的实时行情属于交易所授权收费数据，免费源给延迟快照是行业常态，不是接口的 bug。

**产品含义：TUI 必须逐条标注每个报价的真实延迟。** 而且延迟会浮动，所以要用「响应时间戳 vs 当前市场时钟」
在运行时实算，不能把 15 或 20 分钟写死成常量。把延迟数据显示成实时是本项目明确禁止的行为。

### 交叉验证

新浪 `hq.sinajs.cn`（需带 `Referer: https://finance.sina.com.cn`）对 A股 返回了与腾讯**同一秒**的
时间戳与同样的价格，两个独立源互相印证了 A股 确为实时。新浪同样支持美股（`gb_aapl` 前缀）。
新浪的日经指数代码 `znb_NK225` 返回空串，未找到可用的日股前缀。

**建议：腾讯作主源，新浪作 A股/美股 的备源。** 两家同时挂掉的概率远低于单点。

## 2. 历史 K 线：本项目最大的缺口

### 腾讯 K 线接口有硬上限

```
https://web.ifzq.gtimg.cn/appstock/app/fqkline/get?param=sh600519,day,,,640,qfq
https://ifzq.gtimg.cn/appstock/app/kline/mkline?param=sh600519,m5,,640
```

| 周期 | 实际返回 | 说明 |
|---|---|---|
| 日K | 640 根 | 请求 5000 返回**空**，不是截断 |
| 周K | 640 根 | 同上 |
| 60分K | 320 根 | 上限更低 |
| 5分K | 640 根 | |

指定 `beg`/`end` 日期范围也**不能**突破上限 —— 传 `2010-01-01` 起始返回空响应。

### 美股/日股历史基本不返回

| 请求 | 返回根数 |
|---|---|
| `usAAPL,day,,,640` | **2 根** |
| `jp7203,day,,,640` | **1 根** |

腾讯的 K 线接口实质上只服务 A股 与 港股。

### 为什么这是硬约束

Vegas 隧道依赖 `EMA576`/`EMA676`。EMA 初始种子的残留权重为 `(1-α)^k`，`α = 2/(N+1)`：

| 日线根数 | `EMA576` 种子残留 |
|---|---|
| 640（腾讯上限） | **10.8%** |
| 1330 | 1.0% |
| 2000 | 0.1% |

**640 根算出来的 `EMA576` 有约 11% 来自任意种子，不可用。** 要到 1% 误差需约 1330 根日线（~5.3 年）。

**推论：历史 K 线必须由本项目自行落库并逐日累积，不能每次现拉。** 这直接决定了后端存储设计 ——
Cloudflare 侧需要一个能长期存放多市场多周期 OHLCV 的库，而不只是做缓存。

## 3. 三个已排除的数据源

### 东方财富 `push2his.eastmoney.com` —— 会封 IP
- HTTPS 握手完成后服务端直接断开（`curl` exit 52），IPv4/IPv6 均如此。
- 改走明文 HTTP：**第一次** `lmt=10` 返回 200，随后所有请求（包括 `lmt=5`）全部失败。
- 判定：对海外 IP 有主动封禁策略。**不能作为依赖。** Cloudflare Workers 是共享数据中心 IP，风险更高。

### Yahoo Finance —— 对数据中心 IP 敌视
- `query1/v8/finance/chart/*` 直接 429。
- 走 cookie + crumb 流程：`fc.yahoo.com` 返回 404，`v1/test/getcrumb` 返回字符串 `Too Many Request`。
- 判定：少量请求即触发限流。Workers 出口 IP 被众多用户共享，只会更早触发。**不可作为主源。**

### Stooq —— proof-of-work 验证墙
`https://stooq.com/q/d/l/?s=aapl.us&i=d` 返回 HTTP 200，但 body 是一段要求浏览器计算
SHA-256 前导 4 个零的 JS 挑战，之后 POST `/__verify` 才放行。**不可用。**

## 4. 仍未解决

**美股与日股的历史 K 线还没有可靠的免费源。** 已排除腾讯（无数据）、东财（封 IP）、
Yahoo（限流）、Stooq（PoW）。

这是设计定稿前必须回答的问题。候选方向（尚未实测）：
- 券商类免费档：Finnhub、Alpha Vantage、Twelve Data、Alpaca、Tiingo、Polygon —— 需注册 key，
  多数有每分钟/每日调用上限，且要确认免费档是否给分钟级历史。
- J-Quants（东证官方）日股免费档 —— 需确认其数据滞后期。
- 从 Cloudflare Workers 出口 IP 重测 Yahoo —— 本机 IP 已被限流，不能代表 Workers 的结果。
