## 一页纸架构（阶段 3–5 全局决定，后续各块不得推翻）

这些决定跨越三个阶段，本 spec 只实现其中 A 股的部分，但表结构与抽象要一次建对。

- **顺序：纵向先通。** 先做 A 股端到端闭环（本 spec），再横向铺港美日。理由：A 股有 5990 根全量历史，是唯一能让策略层被真实数据完整检验的市场；先铺市场只会得到三个一律「数据不足」的空壳。
- **扫描范围：各市场热门板块 × 每板块 top 5。** 不做全市场扫描，不只做自选股。
- **候选池：榜单每日重算，历史永久累积。** 标的一旦进过池子，历史留在库里逐日增量更新；「每日重算」的是热度榜与 top5，不是数据。
- **本地 SQLite 为运行时真相源，D1 完整双写同步。** `bars` 只增不改 → 双向 upsert 就是合并，无冲突；`watchlist` / `settings` 带 `updated_at`，最后写入者胜。
- **复权：存原始价 + 因子表，读时复权。** `bars` 永远是原始值。这是「bars 只增不改」得以成立的前提，也让 Worker Cron 的追加永远只写一行。
- **Cron：一个，每小时。** 按市场时钟判断哪个市场刚收盘就追加哪个。四市场共用，不按市场各占一个（账户只剩 4 个）。
- **Worker 写接口用一把共享密钥。** 不是鉴权系统，是门锁。
- **AI：TUI 直连 DashScope OpenAI 兼容端点，不经 Worker，不做 Workers AI 兜底。** key 本来就在本机 `.env`。
- **板块抽象统一。** `sectors(market, code, name, kind)` + `sector_members` 对四个市场通用；粒度差异（A 股几百个概念、港股 4 大类、美股 11 只 ETF、日股 33 业种）体现在数据里而不是 schema 里。
- **后三个市场的池子来源（已查证，2026-09-18）：**
  - 港股：无任何免费机器可读的行业分类。池子 = HSI（88）+ HSCEI（50）成分股，分类为恒生老 4 大类（Wikipedia 表格）。历史腾讯 640 根封顶，靠 Cron 累积。
  - 美股：板块热度 = 腾讯批量报价 11 只 SPDR 板块 ETF（`usXLK` 等，一次请求已实测打通）；板块内成分股 = S&P 500 GICS 分类 CSV（GitHub raw，503 行）。历史 = Alpaca 免费档，邮箱注册即得，日线回溯到 2016 年，不传 `feed=iex` 时默认 SIP 全量成交量（文档里「仅 IEX」的记录是把实时限制误套到了历史上，待更正）。
  - 日股：板块分类 = JPX 官方 `data_j.xlsx`（全市场 33 业种）；池子按 33 业种各取成交额前若干只（Nikkei 官网对程序化访问 403）。历史 = Yahoo 日本站 **history 页**，服务端渲染的标准 `<table id="histlist">`，`from`/`to` 参数可跳到任意年份，实测到 2010 年。Worker 出口对 `.co.jp` 的可达性未测（与已知 429 的 Yahoo 国际站不是同一套 WAF）。
- **降级链（腾讯 → 新浪等）留到下一块**，四个市场一起做「切换 + UI 标注」这套机制。

## Problem Statement

现在的 souba 能看 A 股自选股的实时行情和 K 线、画 MACD/KDJ，但它只能看我已经知道的股票。我没有办法发现我不知道的机会：哪些板块正在被资金持续推动、板块里哪些标的刚刚完成趋势确立、以及为什么。设计文档定义的 Vegas 隧道战法还只停留在文档里，历史 K 线没有落库，每次打开都要重新拉、只能拉到 640 根，`EMA576` 根本算不可信。

## Solution

打开 souba，它在后台自动完成当天的一次扫描：拉新浪的行业与概念板块列表，按「成交额环比放大 + 多日涨幅」算出最热的 8 个板块，每个板块取涨幅前 20 只做候选，缺历史的自动回补新浪的全量日线并用新浪因子做前复权，对每只候选跑 Vegas，按「趋势确立的新鲜度」在每个板块里选出 top 5。按 `s` 进入机会面板，看到板块、标的、`Signal` 的五个维度和每个维度的理由；按 `Enter` 进详情屏看它的 K 线；按 `a` 加自选；按 `i` 让 AI 把这一组 `Signal` 排序并用人话解释——输出明确标注为机器生成的策略分析，不是投资建议。所有历史、板块快照、扫描结果都落本地 SQLite 并同步到 D1；Worker 上一个每小时的 Cron 在 A 股收盘后给每只跟踪过的标的追加当天那根日线，我几天不开机它也在攒。

## User Stories

### 板块与热度
1. 作为使用者，我想让 souba 每天自动拉取新浪的行业板块和概念板块列表，这样我不用自己维护一份板块清单。
2. 作为使用者，我想看到每个板块今天的整体涨幅和成交额，这样我能一眼判断资金在哪。
3. 作为使用者，我想让板块热度综合「成交额相对前几日的放大倍数」和「多日累计涨幅」，这样单日冲高或放量阴跌的板块不会被误判为热门。
4. 作为使用者，我想调整热度公式里两项的权重和回看天数，这样我能按自己的口味校准。
5. 作为使用者，我想让行业板块和概念板块放在同一个榜上比热度，并标注它是行业还是概念，这样我能看出一只股票是概念驱动还是行业驱动。
6. 作为使用者，我想在扫描头几天板块历史不足时热度退化成「只看当日」而不是报错，这样冷启动那几天也有结果看。
7. 作为使用者，我想让每天的板块快照落库，这样多日涨幅和成交额环比有据可算，换机器后也不用从零攒。

### 候选与历史
8. 作为使用者，我想让每个热门板块只取涨幅前 20 只做候选，这样回补历史的量在可控范围内。
9. 作为使用者，我想调整每个板块取多少只候选和最终展示多少只，这样我能在覆盖面和速度之间取舍。
10. 作为使用者，我想让缺历史的候选自动回补新浪的全量日线（5990 根），这样 `EMA576` 有足够的种子长度。
11. 作为使用者，我想让回补自动拉取新浪的前复权因子并在读取时复权，这样除权日不会在 EMA 上砸出假信号。
12. 作为使用者，我想让库里永远存原始价而不是复权价，这样历史永远不需要重写，每次分红也不用整只标的重算落库。
13. 作为使用者，我想让回补严格按节流间隔进行并在被封时指数退避，这样不会因为一次扫描把新浪的接口封掉。
14. 作为使用者，我想让回补进度持久化，这样中途关掉 souba 下次打开能接着补而不是从头来。
15. 作为使用者，我想让一只标的进过池子后历史永久保留并逐日追加，这样它再次上榜时不需要重新回补。
16. 作为使用者，我想让周线从本地日线聚合得出而不是另外拉取，这样周线与日线永远一致且不多占一路请求。

### 策略
17. 作为使用者，我想让 Vegas 策略按设计文档的口诀实现——快隧道 144/169、慢隧道 576/676、EMA12 过滤——这样它就是视频里那套战法而不是变体。
18. 作为使用者，我想让隧道被当作区间而不是线，单根 K 线刺破不算突破，这样它保留抗插针的特性。
19. 作为使用者，我想让 `Signal` 由多个独立维度组成而不是一个分数，这样我和 AI 都能知道「为什么」。
20. 作为使用者，我想看到「趋势」维度——慢隧道向上 / 走平 / 向下，这样我知道该持有还是该离场。
21. 作为使用者，我想看到「共振」维度——日线快隧道在慢隧道上方且周线价格在周线快隧道上方，这样大小周期同步的口诀有落地。
22. 作为使用者，我想看到「位置」维度——价格在快隧道上方 / 隧道内 / 下方，这样我知道有没有做多前提。
23. 作为使用者，我想看到「确认」维度——EMA12 是否也站上了快隧道，这样能区分真假突破。
24. 作为使用者，我想看到「预备」维度——价格还在隧道内或刚触及下沿、但慢隧道已转平转上，这样我能在突破之前就注意到它，同时它不影响主判定。
25. 作为使用者，我想让主判定 `stance` 只由趋势确立与否决定（Long / Watch / Exit / Insufficient），「预备」只是附注，这样机会面板不会把「快要突破」当成买入信号。
26. 作为使用者，我想让日线少于 1330 根时 `stance` 强制为 Insufficient 并说明「慢隧道不可信」，这样它不会拿不够的数据装作有结论。
27. 作为使用者，我想让 Vegas 的所有周期参数、最少根数、新鲜度窗口都可配置，这样我不用改代码就能试不同参数。
28. 作为使用者，我想让 `Strategy` 是一个 trait，Vegas 是它的第一个实现，这样第二个策略进来时不需要动扫描与面板。

### 机会面板
29. 作为使用者，我想按 `s` 进入一个独立的机会面板，这样扫描结果不会污染我手动维护的自选股列表。
30. 作为使用者，我想在面板顶部看到扫描日期和状态（扫描中 x/y、回补中 x/y、完成、失败原因），这样我知道看到的是不是今天的。
31. 作为使用者，我想看到热门板块按热度排序的列表，每行显示板块名、类型、当日涨幅、成交额放大倍数、多日涨幅，这样我能自己判断热度公式选得对不对。
32. 作为使用者，我想展开一个板块看到它的 top 5，每行显示代码、名称、现价、涨幅、`stance`、新鲜度（几根前确立）、五个维度的状态，这样一屏看完不用逐只点进去。
33. 作为使用者，我想让 top 5 按「趋势确立的新鲜度」排序，刚站上的排最前，这样我看到的是刚发生的机会而不是已经走了一段的。
34. 作为使用者，我想让还在回补历史的候选显示「历史回补中」并在补完后自动出现，这样首日扫描不用等 19 分钟才有东西看。
35. 作为使用者，我想让 Insufficient 的标的仍然显示但明确标注「数据不足」，这样我知道它是因为数据不够而不是策略判断不看好。
36. 作为使用者，我想在面板里按 `Enter` 打开该标的的详情屏看 K 线和指标，这样发现机会到看图不用切来切去。
37. 作为使用者，我想在面板里按 `a` 把标的加进自选股，这样看中的机会能一键进入长期跟踪。
38. 作为使用者，我想在面板里按 `r` 手动重跑今天的扫描，这样盘中想更新时不必等明天。
39. 作为使用者，我想让面板在窄屏下砍列而不是画崩，并且 CJK 名称按显示格对齐，这样它跟自选股列表一样在任何终端尺寸下可用。
40. 作为使用者，我想让详情屏能打开不在自选股里的标的（用本地库的历史），这样机会面板的 `Enter` 有地方去。

### 扫描的运行方式
41. 作为使用者，我想让 souba 启动时若今天还没扫描就在后台自动扫，主界面先出来，这样我不用每天第一次打开都干等。
42. 作为使用者，我想有一个 `souba scan` 子命令不带 UI 跑同一套扫描并打印摘要，这样我能挂 launchd 让它盘后自己算好。
43. 作为使用者，我想让同一天重复触发扫描是幂等的（重跑覆盖当天结果），这样后台自动扫和手动 `r` 不会打架。
44. 作为使用者，我想让扫描过程中的行情源出错（新浪返回空、超时）只让本次扫描标记失败并显示原因，不影响自选股看盘，这样看盘这条主路径永远不被扫描拖垮。

### AI
45. 作为使用者，我想在详情屏按 `i` 让 AI 解读这一只标的的 `Signal`，这样我能得到一段人话。
46. 作为使用者，我想在机会面板按 `i` 让 AI 对当天所有板块的 top 5 排序并解释，这样几十条 `Signal` 有人替我读。
47. 作为使用者，我想让喂给 AI 的是算好的结构化 `Signal` 而不是原始 K 线，这样模型负责解释而不负责计算。
48. 作为使用者，我想让 AI 的输出永远带「机器生成的策略分析，不构成投资建议」的标注，这样这个工具不会说谎。
49. 作为使用者，我想让请求关闭思考模式，这样不为 93% 的 reasoning token 付费。
50. 作为使用者，我想让同一组 `Signal` 同一天的回答被缓存，再次打开直接显示，`r` 强制重问，这样一天看几次面板不重复花钱。
51. 作为使用者，我想让 AI 端点不可用时显示「AI 不可用」和原因而不是崩溃或静默，这样它跟行情源挂了是一个待遇。
52. 作为使用者，我想让模型、端点、key 从 `.env` 读取，模型名可配，这样换模型不改代码。

### 配置
53. 作为使用者，我想用 `souba set <key> <value>` 修改任何策略与扫描参数并立即校验，这样不用进 UI 也不用改文件。
54. 作为使用者，我想用 `souba get <key>` 和 `souba settings` 查看当前值和默认值，这样我知道现在跑的是什么参数。
55. 作为使用者，我想让参数存在库的 `settings` 表里并参与 D1 同步，这样两台机器上的参数一致。
56. 作为使用者，我想让非法参数（周期为 0、快隧道比慢隧道还慢、权重为负）被拒绝并说明原因，这样不会把策略配坏了还不知道。

### 同步与 Worker
57. 作为使用者，我想让 souba 启动时从 D1 拉取自上次同步以来的新 bar、板块快照、扫描结果，并合并自选股与设置，这样换一台机器打开就是同一份数据。
58. 作为使用者，我想让扫描结束后把新回补的历史、因子、板块快照、扫描结果推到 D1，这样另一台机器不用重新回补。
59. 作为使用者，我想让 `bars` 的同步是双向 upsert 合并，永远不会因为两边都有而冲突。
60. 作为使用者，我想让自选股和设置按 `updated_at` 合并，后写的赢，这样在另一台机器上加的自选股不会被覆盖丢失。
61. 作为使用者，我想让 Worker 不可达时 souba 照常工作并在顶栏显示「未同步」，这样 Worker 挂了或额度耗尽不影响看盘。
62. 作为使用者，我想让 Worker 的所有写接口要求一个共享密钥，密钥在本机 `.env` 和 Worker secret 里各存一份，这样不会有人扫到 URL 就能清空我的库。
63. 作为使用者，我想让 Worker 上一个每小时的 Cron 在 A 股收盘后用腾讯批量报价接口给库里每只标的追加当天的原始日线，这样几天不开机历史也不断。
64. 作为使用者，我想让 Cron 每次只处理「今天还没追加」的市场，这样同一个 Cron 后续能覆盖四个市场的不同收盘时间。
65. 作为使用者，我想让 D1 与本地 SQLite 用同一套 schema 和同一套迁移，这样不会出现两边结构漂移。
66. 作为使用者，我想让 AI 回答缓存只留在本地不进同步，这样丢了就重问，不占 D1 额度。

### 诚实性（不变量）
67. 作为使用者，我想让每条报价继续标注真实来源与实算延迟，本 spec 不改变这条红线。
68. 作为使用者，我想让任何「数据不足」的判定都显示出来，而不是照样画一条不可信的线。

## Implementation Decisions

### 模块划分

- `core` 新增 `strategy` 子模块：`Strategy` trait、`Signal` / `Facet` / `Stance` / `Adequacy`、`MarketData` 视图、`Vegas` 实现。求值是纯函数，只依赖已排序的复权后 bar 序列与参数。
- `core` 新增 `sector` 子模块：板块热度公式、板块内候选排序、top5 新鲜度排序——全部是对已落库数据的纯计算。
- `core::indicator` 增加周线聚合（按自然周 Mon–Fri，取首开、最高、最低、末收、量求和）。
- `source` 新增新浪板块与因子的抓取与解析：行业列表、概念列表、板块成分股（按涨幅降序取第一页）、前复权因子。抓取共用现有 `Throttle`。
- `source::history` 的 A 股路径明确为「原始价」，不再假装它复权过。
- `store` 扩展 schema（见下）并提供：bars 批量 upsert、按标的读取并复权、因子 upsert、板块与快照、扫描结果、AI 缓存、同步游标、`settings` 带默认值的读写。
- 新增 `scan` 模块：扫描编排（拉板块 → 排热度 → 取候选 → 回补缺失 → 求值 → 排序 → 落库 → 推送同步）。编排层保持薄，可测的逻辑都下沉到 `core::sector` 与 `store`。
- 新增 `sync` 模块：与 Worker 的拉/推，合并规则在 Rust 侧实现为纯函数。
- 新增 `ai` 模块：`Signal` → 提示词的构造（纯函数）、DashScope 调用、缓存查找。
- `ui` 新增机会面板屏；详情屏接受任意本地有历史的标的。
- CLI：现有的手写参数解析扩展为子命令 `scan` / `set` / `get` / `settings` / `sync`；不引入 clap——四个子命令不值一个依赖。
- Worker：从阶段 0 的探测脚本改为正式服务——D1 绑定、同步路由、Cron 处理器、密钥校验。

### Schema（本地 SQLite 与 D1 共用，`PRAGMA user_version` 做迁移）

- `bars(symbol, timeframe, ts, open, high, low, close, volume)`，主键 `(symbol, timeframe, ts)`。**删除 `adjusted` 列**——它是为「存复权价」准备的，那条路不走了。现有库的 `bars` 是空的，迁移直接重建。
- `adj_factors(symbol, effective_date, factor)`：新浪 qfq.js 的累计因子；某日之前的 bar 除以该日对应的因子。
- `sectors(market, code, name, kind, updated_at)`：`kind` ∈ 行业 / 概念（后续市场自行扩展）。
- `sector_daily(market, sector_code, date, change_pct, turnover)`：每日快照，热度公式的输入。
- `sector_members(market, sector_code, symbol, name, as_of, rank)`：当日抓到的板块内涨幅前 K 只。
- `scan_results(date, market, sector_code, symbol, rank, stance, freshness, facets_json)`：机会面板直接读它。
- `ai_cache(key, response, created_at)`：本地，不同步。
- `backfill_state(symbol, timeframe, status, updated_at)`：回补进度，支持断点续补。
- `watchlist` 与 `settings` 增加 `updated_at`；`sync_state(key, value)` 存每张表的最后同步时刻。

### 数据源事实（已实测，实现时不要重新推导）

- 新浪日线 `CN_MarketData.getKLineData` 返回**原始价**（茅台 2024-06-14 新浪 1555.00 vs 腾讯 qfq 1420.66）。因子来自 `realstock/company/{sh600519}/qfq.js`，返回按除权日倒序的累计因子列表。腾讯 qfq 与用新浪因子复权后的结果差约 0.2%，是两家算法差异，不是 bug。
- 新浪行业列表 `q/view/newSinaHy.php`、概念列表 `q/view/newFLJK.php?param=class`：**GBK 原始字节**，一次吐全，字段含板块代码、名称、成分数、涨幅、成交额等（实现时以 fixture 定字段位）。
- 新浪板块成分股 `Market_Center.getHQNodeData?node={代码}&sort=changepercent&asc=0&num=100&page=1`：JSON，中文是 `\uXXXX` 转义（**不是 GBK**），固定 100 条/页。`getHQNodeStockCount` 给总数。**这几个端点不需要 `Referer`**，与日线接口不同，按端点分别处理。
- 全部新浪接口继续强制 HTTP/1.1。日线回补的间隔默认 7 秒，`Throttle` 指数退避。
- Cron 追加用腾讯批量报价 `qt.gtimg.cn/q=...`（阶段 0 已从 Worker 实测可达）：收盘后的报价行就是当天的原始日线（开高低收量额），100 只一批，不逐只请求日线接口。

### 策略与排序

- `Stance`：`Long` = 位置为上方 ∧ 确认为真 ∧ 趋势非向下；`Exit` = 趋势向下；`Insufficient` = 日线根数 < `min_bars`；其余 `Watch`。
- 斜率判定：慢隧道两条 EMA 最近 `slope_window` 根的差值符号，二者同向才算向上/向下，否则走平。
- 新鲜度 = 自「确认」维度从假变真以来的根数；仅对 `Long` 有意义；`fresh_window` 内的排最前，其余按新鲜度升序。
- 板块内 top5 只从 `stance == Long` 里选；不够 5 只时补 `Watch` 中「预备」为真的，并标注。
- 热度 = `w_turnover × (今日成交额 / 前 N 日均值) + w_change × N 日累计涨幅`；快照不足 N 日时按实际天数算，0 日时退化为当日涨幅。
- 默认参数：`vegas.filter=12`、`vegas.fast=144,169`、`vegas.slow=576,676`、`vegas.min_bars=1330`、`vegas.slope_window=5`、`vegas.fresh_window=3`、`scan.sectors=8`、`scan.k=20`、`scan.top=5`、`scan.heat_days=5`、`scan.w_turnover=1.0`、`scan.w_change=1.0`。

### 扫描编排

- 触发：TUI 启动时若 `scan_results` 无今日记录则后台启动；`souba scan` 子命令；面板 `r`。同日重跑覆盖。
- 后台任务通过通道向 UI 报进度（阶段、x/y），UI 只读状态不阻塞。
- 回补队列按候选顺序，逐只完成即刻可被求值与展示；`backfill_state` 记录进度。
- 任何单只失败只标记该只，扫描继续；板块列表拉取失败则本次扫描整体失败并保留昨日结果。

### AI

- OpenAI 兼容 chat completions，`enable_thinking: false`，`stream` 关闭。
- system 提示词固定：Vegas 口诀、`Signal` 各维度的含义、输出必须以「机器生成的策略分析，不构成投资建议」开头。
- user 内容为 `Signal` 的 JSON（单只或一组）。
- 缓存键 = 输入 JSON 的 SHA-256 + 日期。
- 回答渲染在详情屏 / 面板的一个可滚动文本区，CJK 按显示格折行。

### 同步协议（Worker）

- 请求头 `X-Souba-Key`，不匹配 401。
- `POST /sync/bars` 批量 upsert；`GET /sync/bars?since=` 按 `ts` 增量拉。
- `GET|PUT /sync/watchlist`、`/sync/settings`：整表交换，客户端按 `updated_at` 合并后回写。
- `POST|GET /sync/sectors`：`sectors` / `sector_daily` / `sector_members` / `scan_results` / `adj_factors` 的增量交换，按 `updated_at` 或 `date` 游标。
- Cron `0 * * * *`：读 D1 里 `bars` 的 distinct 标的，按市场时钟判定「已收盘且今日未追加」的市场，分批 100 只批量报价，写入当日原始日线。本块只实现 A 股分支，结构预留其余市场。

## Testing Decisions

好的测试只断言外部行为：给定输入字节/序列/状态，得到什么解析结果、什么 `Signal`、什么排序、什么渲染文本。不断言内部调用顺序。

**沿用的既有 seam（都已有先例）：**
1. **解析器 fixture**：真实响应字节 → 类型化结果（先例：腾讯报价 `parse_batch`、新浪日线 `parse_sina_cn`）。新增：行业/概念列表（GBK）、板块成分股（JSON 转义）、qfq.js 因子。
2. **内存 SQLite**：`Store::open_in_memory()` 上做读写断言（先例：自选股测试）。新增：bars upsert 幂等、读时复权数值、因子更新后重读结果变化、快照与扫描结果、`updated_at` 合并、迁移从旧 `user_version` 升上来不丢自选股。
3. **渲染 Buffer**：`render_at(w, h)` → 文本断言（先例：自选股表格、详情屏）。新增：机会面板各尺寸不 panic、每行宽度等于终端宽、CJK 对齐、扫描状态文案、Insufficient 与回补中文案。
4. **纯计算**：手算对照（先例：EMA/MACD/KDJ）。新增：周线聚合、热度公式、新鲜度排序。

**新增的 seam：**
5. **`Strategy::evaluate`**：构造能得出已知 EMA 关系的合成 bar 序列，断言五个维度与 `stance`；不足 1330 根断言 `Insufficient`；单根刺破不改变位置维度。这是策略层唯一的测试入口，扫描编排不另起 seam——编排保持薄，其可测部分全部落在 seam 4 与 2。
6. **Worker**：用 `@cloudflare/vitest-pool-workers` 跑本地 D1，断言路由的 upsert 语义、401、Cron 处理器对「已收盘/未追加」的判定。这是 Worker 侧第一个测试，也是本 spec 唯一的新依赖，理由：Worker 从探测脚本变成有状态服务，没有测试的 Cron 出错会静默断历史。

联网冒烟测试沿用现有做法：`#[ignore]`，手动跑。
