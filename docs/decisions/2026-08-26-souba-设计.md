## 1. 这是什么

一个跑在终端里的多市场股票行情与策略终端。四个市场（A股/港股/美股/日股）的行情、
多周期 K 线与可配置指标、可插拔的选股策略、以及一个用策略结果做推荐的大模型。

**纯自用单人工具。** 这条决定是承重的：不做鉴权、不做多租户、不做配额。

## 2. 三条决定架构的约束

调研阶段实测出来的，不是假设：

1. **Cloudflare 免费版 10 ms CPU 上限，Worker / Durable Object / Cron 一视同仁。**
   在 Worker 里 `JSON.parse` 一批 K 线就可能吃掉大半预算。
   → **一切计算下沉到客户端。**
2. **免费行情源会因连续请求封 IP。** 实测新浪约 10 次快速请求即返回空，东财直接长时间拒绝。
   → **数据层必须自带节流、缓存、退避。**
3. **各市场的实时性天差地别，且延迟会漂移。** A股/港股可得真实时，日股只有爬 Yahoo 日本站，
   否则慢 15–20 分钟。
   → **延迟必须运行时实算并在 UI 逐条标注。**

## 3. 分层

```
┌─ souba (Rust, 单静态二进制) ──────────────────────────────┐
│  adapter   四市场数据接入，各自的降级链与节流               │
│  engine    指标计算 + 策略求值                             │
│  store     本地 SQLite：自选股、K线、配置                   │
│  ui        ratatui 渲染，自适应终端尺寸                     │
└───────────────┬──────────────────────────────────────────┘
                │ HTTPS（仅历史落库与 AI，实时行情不走这里）
┌───────────────▼──────────────────────────────────────────┐
│  souba-worker (TypeScript)                                │
│   D1      多市场多周期 OHLCV 长期累积                       │
│   Cron    收盘后每标的追加 1 根（payload 小，10 ms 够）      │
│   ai      LLM 代理，隐藏 key                                │
└──────────────────────────────────────────────────────────┘
```

**Worker 是存储层和代理层，不是计算层。**
本地 SQLite 与 D1 共用同一套 schema：断网时用本地库照常看盘，联网时同步。
**Worker 挂掉或额度耗尽都不影响看盘** —— 这是免费版下正确的降级姿态。

## 4. 数据接入层

### 4.1 各市场的源与降级链

| 市场 | 实时行情（主 → 备） | 历史 K 线 |
|---|---|---|
| **A股** | 腾讯 `sh600519` → 新浪 `list=sh600519` | 新浪 `CN_MarketData` **全量（5990 根日线）** |
| **港股** | 腾讯 `r_hk00700` → 新浪 `rt_hk00700` | 腾讯 `ifzq` 640 根 → 自行累积 |
| **美股** | 腾讯 `usAAPL` → Alpaca | **Alpaca**（官方 API，深度够） |
| **日股** | **Yahoo 日本站**（爬取）→ 腾讯 `jp7203`（延迟 15–20 分钟） | **尚无可用源**，见 §11 |

**注意事项（全部实测得出）：**

- 腾讯/新浪返回 **GBK**，必须显式解码，否则股票名乱码。
- 港股实时**必须**用 `r_` / `rt_` 前缀，同主机上的裸前缀是 15–22 分钟延迟的孪生接口。
- 新浪深历史接口是 `money.finance.sina.com.cn/quotes_service/.../CN_MarketData`，
  **不是** `quotes.sina.cn/.../CN_MarketDataService`（后者 1800 根封顶）。
  两者都**必须强制 HTTP/1.1**，走 HTTP/2 会挂住不返回。
- 新浪报价接口**硬性要求 `Referer` 头**，缺了直接 403。
- **前复权必须处理**（腾讯 `qfq` 参数）。不复权的话除权日会在 EMA 上砸出假信号。

### 4.2 批量刷新

腾讯报价接口支持一次最多 **100 只、可混合市场**：

```
qt.gtimg.cn/q=sh600519,sz000001,r_hk00700,usAAPL,jp7203
```

**整个自选股列表一次请求刷新完**，不按市场拆分，不逐只轮询。
这同时把封 IP 的风险降到很低。

### 4.3 代码归一化

四个市场的代码格式互不兼容，同一只股票在不同源里还有不同写法。
内部统一成 `市场:代码`，各 adapter 负责与外部格式互转：

| 内部 | 腾讯 | 新浪 | Yahoo | 说明 |
|---|---|---|---|---|
| `CN:600519` | `sh600519` | `sh600519` | `600519.SS` | 沪市，`sh`/`sz`/`bj` 由代码段推导 |
| `HK:00700` | `r_hk00700` | `rt_hk00700` | `0700.HK` | 内部保留 5 位前导零 |
| `US:AAPL` | `usAAPL` | `gb_aapl` | `AAPL` | 新浪用小写 |
| `JP:7203` | `jp7203` | — | `7203.T` | 新浪不支持日股 |

**归一化是 adapter 的职责，engine 与 ui 只见内部格式。**

### 4.4 每个 adapter 的契约

```rust
pub trait QuoteSource {
    fn id(&self) -> &str;
    /// 批量取报价。实现者负责节流；返回的每条 Quote 必带 source 与实算的 age
    async fn quotes(&self, symbols: &[Symbol]) -> Result<Vec<Quote>>;
}

pub struct Quote {
    pub symbol: Symbol,
    pub last: Decimal,
    pub prev_close: Decimal,
    pub open: Decimal, pub high: Decimal, pub low: Decimal,
    pub volume: u64, pub turnover: Decimal,
    /// 数据源返回的时间戳，已归一到 UTC
    pub stamped_at: DateTime<Utc>,
    /// 由 stamped_at 与市场时钟实算得出，不是常量
    pub age: Duration,
    /// 哪个源给的 —— UI 必须能显示
    pub source: SourceId,
}
```

**降级必须可见。** 主源失败切备源时，UI 立刻反映当前用的是哪一档，
尤其日股（Yahoo 一发版就断）。**绝不允许爬虫坏掉后静默显示陈旧价格。**

### 4.5 节流

统一令牌桶 + 指数退避，按 host 分桶（腾讯与新浪各自独立）。
盘中刷新间隔默认 3 秒 —— A股 Level-1 本身就是 3 秒快照，更快没有意义。
非交易时段自动降频。

## 5. 存储

本地 SQLite 与 D1 共用 schema：

```sql
CREATE TABLE bars (
  symbol     TEXT NOT NULL,     -- 归一后的内部代码，如 CN:600519 / HK:00700
  timeframe  TEXT NOT NULL,     -- 1d 1w 1mo 60m 30m 15m 5m
  ts         INTEGER NOT NULL,  -- bar 起始时刻，UTC epoch 秒
  open REAL, high REAL, low REAL, close REAL, volume REAL,
  adjusted   INTEGER NOT NULL,  -- 是否前复权
  PRIMARY KEY (symbol, timeframe, ts)
) WITHOUT ROWID;

CREATE TABLE watchlist (
  symbol TEXT PRIMARY KEY, name TEXT, sort_order INTEGER, added_at INTEGER
);

CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT);
```

**冷启动回补由 TUI 做**（本地无 CPU 限制），拉到后分批 POST 给 Worker。
**Cron 只做每日增量追加** —— 每标的每周期新增 1 根，10 ms 足够。

D1 免费版单库 500 MB、每日写入 10 万行。算一下量级：

| 周期 | 每标的每交易日新增 | 100 只标的/天 |
|---|---|---|
| 日线 | 1 根 | 100 行 |
| 60分 | 约 4 根（A股 4 小时） | 400 行 |
| 15分 | 16 根 | 1,600 行 |
| 5分 | 48 根 | 4,800 行 |

全上也才约 6,900 行/天，远低于 10 万上限。**所以四个周期都上 D1**，
不需要区别对待。真正的约束是 500 MB 单库容量 —— 按每行约 60 字节估，
100 只标的存满 5 年的全部周期约 200 MB，仍在范围内。到顶时先淘汰 5 分钟线的远端数据。

## 6. 指标引擎

Rust 侧用 **`yata`**（Apache-2.0，流式增量更新，3–200 ns/次）。

- **`yata` 维护状态是黄灯**（最后发版 2024-03）。备选 `ta-rs`（下载量最大，同样久未发版）。
  两者都够用且 API 稳定，风险可接受；真出问题时指标算法本身也不难自己实现。
- **KDJ 自己推导**：`yata` 提供 Stochastic 的 K/D，`J = 3K - 2D` 一行即可。
  不为这一行引入一个新库。

指标参数全部可配（周期、快慢线、信号线等），存 `settings` 表，不硬编码。

## 7. 策略引擎

### 7.1 抽象的形状

策略做抽象。为了不让它变成「围着 Vegas 长出来的伪抽象」，
下面的 trait 用 MACD 金叉、KDJ 超买超卖、布林带突破三个策略反向检验过。

```rust
pub trait Strategy: Send + Sync {
    fn id(&self) -> &str;
    fn name(&self) -> &str;

    /// 需要哪些周期的数据。Vegas 需要多周期（口诀三提到大小周期同步）
    fn required_timeframes(&self) -> &[Timeframe];

    /// 结果可信所需的最少 K 线根数。EMA576 → 1330
    fn min_bars(&self, tf: Timeframe) -> usize;

    /// 参数规格：UI 据此生成配置界面，配置文件据此校验
    fn param_specs(&self) -> &[ParamSpec];
    fn configure(&mut self, params: &ParamMap) -> Result<()>;

    /// 求值。必须廉价 —— 全市场扫描会调用几千次
    fn evaluate(&self, data: &MarketData) -> Signal;
}

/// 策略求值的输入。按周期提供已排序的 K 线与最新报价。
/// 由调用方保证 required_timeframes() 声明的周期都已装载。
pub struct MarketData<'a> {
    pub symbol: &'a Symbol,
    pub quote: Option<&'a Quote>,          // 盘中有，回测时为 None
    bars: &'a HashMap<Timeframe, Vec<Bar>>, // 时间升序
}

impl<'a> MarketData<'a> {
    pub fn bars(&self, tf: Timeframe) -> &[Bar];
    pub fn len(&self, tf: Timeframe) -> usize;
}
```

### 7.2 Signal：不合成单一分数

```rust
pub struct Signal {
    /// 主判定
    pub stance: Stance,          // Long | Watch | Exit | Insufficient
    /// 策略自定义的若干正交维度，各自独立可解释
    pub facets: Vec<Facet>,
    /// 数据是否够。不够时 stance 强制为 Insufficient
    pub adequacy: Adequacy,
}

pub struct Facet {
    pub label: String,           // "趋势" / "共振" / "位置" / "确认"
    pub state: FacetState,       // Bullish | Neutral | Bearish
    pub detail: String,          // "慢隧道向上倾斜 (576:1211.0 676:1218.3)"
}
```

**为什么不给一个 0–100 分**：各维度失效的原因不同，合成之后就没法说清「为什么」，
而「为什么」正是要喂给大模型的东西。这条对所有策略成立，不只 Vegas。

### 7.3 首个实现：Vegas 隧道

```
EMA12              过滤器
EMA144 / EMA169    快隧道 —— 价格在其上方是做多的唯一前提
EMA576 / EMA676    慢隧道 —— 决定持仓与离场（= 快隧道 × 4）
```

四个 facet：

| facet | 判据 |
|---|---|
| 趋势 | 慢隧道 576/676 的斜率：↗ 向上 / → 走平 / ↘ 向下 |
| 共振 | 快隧道是否位于慢隧道上方 |
| 位置 | 价格 vs 快隧道区间：上方 / 隧道内 / 下方 |
| 确认 | `EMA12` 是否也站上快隧道（区分真假突破） |

**隧道是区间不是线。** 单根 K 线短暂刺破不算有效突破 —— 这是它抗插针的全部原因，
任何把隧道塌缩成单根均线的实现都丢掉了这套战法。

### 7.4 边界：参数可配，逻辑用 Rust 写

「灵活配置策略」在本版本的含义是**参数可配置**（周期、阈值、启用的 facet），
**不是**用户可以写脚本定义新策略。嵌 Rhai/Lua 做用户脚本是另一个量级的工作，
等真的需要第三、第四个策略时再评估。

### 7.5 数据充足性必须显式

日线 `EMA576` 少于 1330 根时，`stance` 强制为 `Insufficient`，
UI 标注「数据不足，慢隧道不可信」，**而不是照样画一条线**。

A股 有 5990 根，不触发。**港股（640 根）、美股、日股初期都会触发** —— 这是诚实的做法，
随着 D1 逐日累积会自动解除。

## 8. TUI

### 8.1 自适应铺满

`Constraint::Fill` 为主，不用固定行列数；`SIGWINCH` 实时响应尺寸变化。

```
宽屏 ≥120列            中屏 80–119列        窄屏 <80列
┌────────┬──────────┐  ┌──────────────┐   ┌──────────┐
│自选股   │ K线 + 指标 │  │  自选股列表    │   │ 自选股    │
│        ├──────────┤  ├──────────────┤   │ (精简列)  │
│        │ 策略 / AI │  │  K线 + 指标    │   └──────────┘
└────────┴──────────┘  └──────────────┘    K线需切屏
```

- 列优先级：代码 > 现价 > 涨幅 > 名称 > 涨跌额 > 成交额。窄屏从右往左砍。
- **CJK 宽度按显示格算，不是码点** —— 「贵州茅台」占 8 格。用 `unicode-width`。
  这是正确性问题不是美观问题：算错会让每一行都错位。
- K 线区按剩余宽度动态计算可显示根数；braille 点阵做子像素。
- 小于 80×24 显示提示，不画崩。
- 顶栏逐市场显示**实算的**延迟与当前数据源。

## 9. AI 层

Worker 代理，默认 `qwen3.7-flash`，模型可配（OpenAI 兼容端点）。
兜底 Cloudflare Workers AI `@cf/qwen/qwen3.8-27b`（免费额度 10,000 neurons/天 ≈ 73 次/天）。

**两件必须做的事：**

1. **关掉思考模式。** 实测 `qwen3.7-flash` 一次简单问答 840 个输出 token 里 **784 个是 reasoning**（93%），
   全部按输出价计费。
   - DashScope：`enable_thinking: false`
   - Workers AI：`chat_template_kwargs: {"enable_thinking": false}`
     （顶层的 `enable_thinking` 会被**静默忽略**，实测无效）
2. **喂给模型的是策略算好的结构化 `Signal`，不是让模型自己看 K 线。**
   模型负责解释与排序，不负责计算。

输出**必须标注为机器生成的策略分析，不是投资建议**。

## 10. 分阶段实施

| 阶段 | 交付 | 完成标准 |
|---|---|---|
| **0** | Worker 出口 IP 可达性实测 | 部署最小 Worker，确认能否拉到腾讯/新浪数据 |
| **1** | A股 + 自选股 + TUI 实时刷新 | 能看盘 |
| **2** | 指标引擎 + K 线渲染 | MACD/KDJ 数值与 TradingView 对得上 |
| **3** | 港股/美股/日股 + 降级链 | 四市场可用，降级时 UI 正确标注 |
| **4** | D1 历史累积 + 策略引擎 + Vegas | 数据充足性检查生效 |
| **5** | AI 推荐 | — |

**阶段 0 是前置条件。** 所有数据源测试都来自一台日本住宅 IP，
Worker 侧（共享数据中心 IP）完全未验证。Yahoo 已证实对这类 IP 第一个请求就 429。
